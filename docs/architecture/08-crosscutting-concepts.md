# 8. Crosscutting Concepts

Concepts that apply across all modules. Most are implemented in the shared kernel,
`Ouranos.Pantheon.Modules.Shared.Contract`, whose internals are documented in the
[Shared module docs](../../src/modules/shared/docs/README.md). This section states the rules
every module follows; how a module applies them is documented by that module (see
[Section 5.3](05-building-block-view.md#53-blackboxes-modules)).

## 8.1 Domain Primitives

| Abstraction | Purpose |
|-------------|---------|
| `Id<T>` | Strongly-typed record struct wrapping a string (`Id<Market>` ≠ `Id<Symbol>`; a GUID by convention, generated by the `DatabaseExtensions.CreateId<T>()` factory), with JSON converter; binds directly from route/query values |
| `BaseEntity<TId>` | `Id`, `CreatedAt`, `UpdatedAt`, protected `Update()` touch |
| `BaseEventSourcedEntity` | Marten aggregate base with Guid stream key |
| `IDomainEvent` | Marker for domain events |
| `OperationResult<TAggregate>` | New aggregate state plus the domain events to append, returned by event-sourced (Hestia) operations. Not a success/failure result type |

## 8.2 Application Patterns

- **Handler markers**: `IPantheonHandler<TInput, TOutput>` (query/command),
  `IPantheonHandler<TInput>` (fire-and-forget, e.g. RabbitMQ consumers),
  `IPantheonStreamHandler<TInput, TOutput>` (streaming). Wolverine discovers
  implementations by scanning module assemblies for these markers; there is no mediator
  registration to maintain.
- **Endpoint dispatch**: every endpoint's `Handle` calls `IMessageBus.InvokeAsync<T>`;
  slices never call each other's handlers.
- **Common query contract**: paging (`skip/take`, bounded by `QueryOptions`), sorting, and
  the `field:op:value` filter language, parsed once in the kernel and reused by most list
  endpoints. A few lists support only part of the contract; the Bruno collection shows
  each endpoint's parameters.
- **Table search**: there is no search engine. The frontend data table has one search box.
  Plain words become a text search: an `or(col:like:term|…)` group over the table's
  `searchable` columns, which default to string columns that support `contains`. Typed
  conditions (`Volume > 1000`) are mixed in and implicitly ANDed. The result is sent through
  the same filter language, so search needs no backend changes. The visual filter builder
  edits the same tree from a dialog.
- **Global search**: the top-bar command palette (Ctrl/⌘+K) has no search endpoint either.
  It sends a `name:like:term` filter to the existing list endpoints of every module, drops
  any source that fails, and adds static pages and actions filtered in the browser.
- **Step pipeline**: `IStep`/`StepRegistry` abstractions in the kernel compose a chain of
  responsibility pipeline. No module uses it today
- **Polymorphic JSON columns**: a configuration whose shape depends on a discriminator is
  one `jsonb` column via `HasJsonConversion`, stored in the same camelCase, string-enum
  shape the API uses; adding a field needs no migration
- **Shared Algorithms**: generic algorithms (`Algorithms/`, e.g. the genetic-algorithm
  engine) live in the kernel so any module can use them

## 8.3 Persistence

- **Schema-per-module**: each `OuranosDbContext` subclass declares its Postgres schema
  (`plutus`, `hermes`, …); EFCore.NamingConventions enforces snake_case.
- **Two persistence styles, one engine:**
  - *Relational + time-series* (Plutus, Hermes, Shared): EF Core, with TimescaleDB
    hypertables and continuous aggregates where data is time-series. Migrations per module,
    applied in module `Configure`.
  - *Documents and events* (Hestia): Marten event streams with inline snapshots, and plain
    Marten documents.

  Which style a module uses is a platform decision
  ([ADR 0004](../adr/0004-polyglot-persistence-on-postgresql.md)); how it models its data is
  documented by the module.
- **`PostgresModule`**: `AddCorePostgresModule<TContext>()` / `ApplyCorePostgresMigrations<TContext>()`
  provide the shared DAL registration/migration path so modules stay consistent.
- TickerQ's operational store is a separate context, migrated centrally in `UseOuranosCore`.

## 8.4 Messaging (Wolverine + RabbitMQ)

When `Ouranos:RabbitMq:Host` is set, conventional local routing is disabled and every
published message declares its topology as constants on the message type. Without a host,
no RabbitMQ transport is configured and Wolverine routes messages locally. `AutoProvision`
creates exchanges/queues at startup (`AutoCreate.CreateOrUpdate` in production).

Topology is named per module: exchange `<module>.<topic>`, queue
`<module>.<topic>.<action>`, dead-letter queue `<queue>.dlq`. Each module lists its messages
in its module README.

**Error policy** (centralized in `CoreExtensions`, registered only when `Ouranos:RabbitMq:RetryCount`
is set): `ArgumentException` and
`InvalidOperationException` move straight to the error queue (they indicate bugs/bad
input, not transient faults); any other exception retries with fixed cooldown intervals
(configured via `Ouranos:RabbitMq:RetryCount`, 250 ms steps) before dead-lettering.
Consumers of long-running work record failures on their entity instead of throwing, so
their DLQs only see infrastructure faults.

All messages today are module-internal async flows; no message crosses module boundaries.
A message that did would be a platform-level contract and documented here.

## 8.5 Scheduling (TickerQ)

In-process scheduler with EF Core store and dashboard at `/tickerq/dashboard`
([Section 6.1](06-runtime-view.md#61-scheduled-jobs)). Each module lists its own jobs in its
module README.

## 8.6 Errors and Validation

- No FluentValidation. Guards are `Ardalis.GuardClauses` in constructors/handlers
  (`Guard.Against.Null`, `Guard.Against.NotFound`, …) plus domain invariants.
- `services.AddProblemDetails()` is registered, and `UseExceptionHandler()` turns unhandled
  exceptions into ProblemDetails responses. Two exceptions are mapped:
  - `InvalidFilterException`, which `FilterBy` raises for a filter it cannot parse, a filter on
    an unregistered field, or a value it cannot convert. `InvalidFilterExceptionHandler`
    returns it as **400 Bad Request**.
  - `ConflictException` (`Shared.Contract`, `Application.Common`), which a domain operation
    throws when the request conflicts with the resource's current state (e.g. reimporting a
    recipe that is still importing). `ConflictExceptionHandler` returns it as
    **409 Conflict**.

  Everything else stays 500.
- The messaging error policy above handles async failure classification.

## 8.7 Logging

Serilog with configuration-driven setup; `UseSerilogRequestLogging` for HTTP. Convention:
`LogTrace` at handler entry, `LogDebug` on success, structured message templates with
named placeholders (`'{paramName}'`). Production ships to Loki; Serilog SelfLog echoes
configuration problems to stderr. Log events carry `TraceId`/`SpanId` automatically when
an OpenTelemetry activity is current; the Grafana Loki sink writes them into the JSON log
body, linking Loki entries to spans (see 8.14).

## 8.8 API Conventions

- Routes are `/api/<module>/...`; `/health` is the only unprefixed route
- camelCase JSON with `JsonStringEnumConverter` and `IdJsonConverterFactory` for `Id<T>`
- Async operations return **202 Accepted** with a `Location` header pointing at the
  resource to poll ([Section 6.3](06-runtime-view.md#63-scenario-asynchronous-long-running-work))
- Streaming endpoints (chat completion, module assistants) use Server-Sent Events
- Query binding is case-insensitive to input record property names
- Bruno collection in
  `bruno/` documents every endpoint's concrete shape

## 8.9 Feature Flags and Configuration

Flagsmith is registered centrally (`AddCoreFlagsmithModule`) and consumed through
`IFlagsmithClient` where behavior toggles matter
([ADR 0012](../adr/0012-feature-flags-via-flagsmith.md)). Each flag carries the owning
module's prefix and is documented by the module that reads it.
The client caches environment flags for `CacheDurationMinutes` (default 1), so a request
reaches Flagsmith at most once per interval, and uses a short request timeout and few
retries. When Flagsmith is unreachable, or a flag does not exist, the client falls back to
`Ouranos:Flagsmith:DefaultFlags` (flag name to enabled state); flags not listed there read as
disabled. A module whose flag guards data exposure lists it there as enabled so that it fails
closed. The fallback result is cached like any other, so recovery takes up to one interval.
Configuration binds through typed option classes per section under the `Ouranos:` root
(e.g. `RabbitMqOptions`, `PostgresOptions`, `QueryOptions`, `HealthOptions`); each module
binds its own section `Ouranos:<Module>` and documents it in its module README.
`IMemoryCache` is registered centrally in `AddOuranosCore`; HTTP response caching is
separate (8.10).

## 8.10 Response Caching (OutputCache)

The Shared module wires the mechanism only (`AddOutputCache()` / `UseOutputCache()` in
`CoreExtensions`, with a base policy that varies by the `Origin` header); each endpoint
configures its own caching inline at the mapping site
via `.CacheOutput(policy => ...)`, so route, binding, and cache behavior live together
in the slice's endpoint file. Use it for endpoints whose response is expensive to
compute but tolerates bounded staleness (dashboard aggregates, listings behind
read-heavy UIs), never for user-specific or rapidly-changing data. Policies carry an
expiry and vary by their query parameters; reference those with
`nameof(InputSchema.Property)` so the vary-by keys stay strongly typed and track the
input schemas the endpoints bind from. Consequently identical requests collapse into
a single computation per TTL window, and caching an endpoint requires no changes
outside its endpoint file. The exception is a cached response that must not outlive a
write: the entry is tagged and the writing endpoint calls
`IOutputCacheStore.EvictByTagAsync` for that tag after the handler succeeds, so the
cache stays an HTTP concern and handlers never see it. Use a static `.Tag(...)` on the policy
when any write invalidates every entry; when only one entity's entries go stale, the
endpoint adds a per-entity tag through `IOutputCacheFeature.Context.Tags`, so updating or
deleting one entity evicts only its own entries. See
[ADR 0010](../adr/0010-server-side-output-caching-for-dashboard-aggregates.md) for the
motivating case.

## 8.11 Real-Time Infrastructure

The kernel's `WebSockets/` package generalizes long-lived connections: listener registry,
reconnecting client, serializers, and the `WebSocketWorker` hosted service. A module hosts
a worker per feed via factory methods in its `Build`; connection state is surfaced to
health checks through `WebSocketHealthState`.

Outbound streaming uses `SseWriter` (kernel) with `IPantheonStreamHandler`.

### AI Assistants

Modules embed contextual chat assistants through the kernel's `Application/Assistants/`
package (`PantheonAssistant<TContext>`, mapped with `MapAssistant`). The governing rule:
prompts, model settings, and domain data stay on the server - the client sends only
conversation history and typed context references, so no endpoint becomes an open proxy to
the inference host and answers are grounded in the module's own store rather than
client-supplied data. Every module's assistants follow these rules:

- **Layout**: everything assistant-related sits in the module's `Features/Assistants/`: one
  `Ask<Assistant>/` folder per assistant, a tool catalogue in `Tools/`, and the context
  interfaces tools are typed to in `Scopes/`.
- **Per-module tools**: tools call only their own module's handlers; there are no
  cross-module tools.
- **Proposals, not writes**: a tool never changes data. Every action is a proposal the user
  applies or rejects, and data changes go through the module's normal update endpoint.
- **Page-scoped and budgeted**: one assistant per page, seeing only what the page shows,
  with a small tool set, because the self-hosted model's context window is limited.
- **Stateless**: the client resends the conversation each turn; nothing is persisted.
- **Model defaults are central**: `ModelDefaults` holds the global model, effort and token
  defaults; features override only what they need.

Hermes chat is not a page assistant: it is the user's own general-purpose chat, so it sends
its persona, model settings and history from the client and persists its conversations. It
reuses the same tool loop, tool abstraction and event contract
([Hermes module docs](../../src/modules/hermes/docs/README.md)).

The framework's mechanics (tool loop, event contract, history trimming, frontend panel) are
documented in the [Shared module docs](../../src/modules/shared/docs/README.md). Each module
documents its own assistants and their tools. The runtime flow is
[Section 6.4](06-runtime-view.md#64-scenario-module-assistant-turn).

## 8.12 Health Checks

Registered centrally in `AddOuranosCore`: Postgres, RabbitMQ, OuranosMl, WebSocket state,
and TickerQ, run in parallel behind a single `GET /health` endpoint. The checks implement
the Shared module's own `IHealthCheck` interface, not the
`Microsoft.Extensions.Diagnostics.HealthChecks` one.

## 8.13 Security

There is no authentication or authorization anywhere in `src/`. This is by design for a
single-operator homelab deployment; see
[ADR 0008](../adr/0008-no-authentication-single-user.md) and risk D2 in
[Section 11](11-risks-and-technical-debt.md). Anything that can reach the gateway port
has full access. The controls that do exist:

- **CORS allow-list** (`CorsAllowedHosts`, policy `AllowLocalAndServer`, see 7.3). It
  limits which browser origins may call the API; it does nothing against non-browser
  clients.
- **Anti-SSRF guard** on Hestia's recipe scraper, so imported URLs cannot reach internal
  hosts.

## 8.14 Observability (OpenTelemetry)

The gateway emits OpenTelemetry traces and metrics, registered centrally in `AddOuranosCore`
via `AddCoreObservabilityModule` (Shared module, `Infra/Observability/`,
[ADR 0009](../adr/0009-opentelemetry-observability-via-otlp.md)). Logs stay on the
Serilog → Loki pipeline.

Tracing:

| Aspect | Configuration |
|--------|---------------|
| Sources | ASP.NET Core (excludes `/health` and `/tickerq`), HttpClient, Npgsql, ActivitySources `Wolverine`, `Marten`, `TickerQ` (official `TickerQ.Instrumentation.OpenTelemetry` package), and `Ouranos.Pantheon.WebSockets` (shared `WebSocketTelemetry`) |
| Sampling | `RootSpanExclusionSampler` → `ParentBasedSampler` → `TraceIdRatioBasedSampler`: root spans (no parent) named in `Ouranos:Observability:ExcludedRootSpanNames` (default `postgresql`, `CONNECT *`, `wolverine_node_assignments`, `rabbitmq connect`; trailing `*` = prefix) are dropped so background infrastructure work starts no traces; ratio from `Ouranos:Observability:SamplingRatio` (default 1.0) governs everything else |
| Resource | `service.name` from `ObservabilityOptions.ServiceName`, `deployment.environment.name` from the host environment |
| Exporter | OTLP to `Ouranos:Observability:OtlpEndpoint` over `grpc` (default) or `http/protobuf` (`Ouranos:Observability:OtlpProtocol`) (production: the Grafana stack's Alloy receiver); skipped when unset and `OTEL_EXPORTER_OTLP_ENDPOINT` is not present |

Wolverine injects/extracts trace context on RabbitMQ envelopes, so a request trace spans
HTTP → message publish → consumer handler → database calls. TickerQ job executions are
root spans wrapping their own HTTP/DB work. WebSocket loaders emit `websocket connect` /
`websocket disconnect` spans and one `websocket message` consumer span per received
message (deserialize + dispatch, tagged with host/message type/size); the message span
is a trace root by design (the receive loop runs inside the connect span's ambient
context, and without clearing it every message of a session would parent to that span,
producing one unbounded megatrace per connection), so `SamplingRatio` also throttles
feed traces. Publishes from listeners inherit the message span, so socket → RabbitMQ →
consumer → Postgres is one trace per message.

Metrics (same exporter gating as traces):

- Library meters: ASP.NET Core, HttpClient, Kestrel, `Npgsql`,
  `Microsoft.EntityFrameworkCore`, `Marten`, `Wolverine*` (wildcard required - the
  meter name embeds the application name), and runtime metrics via
  `OpenTelemetry.Instrumentation.Runtime`
- WebSocket meter (`Ouranos.Pantheon.WebSockets`): messages received/sent, dispatch
  duration, message size, active connections and reconnects by worker - instrumented
  once in the shared WebSocket abstractions (`WebSocketTelemetry`,
  `WebSocketClient`, `ListenerRegistry`, `WebSocketHealthState`); feed code is
  untouched

Wolverine tracking opt-ins: `HandlerExecutionDiagnosticsEnabled` (handler start/finish
events, transport-lag tags) and `OutboxDiagnosticsEnabled` (Marten outbox flushing
spans). `DeserializationSpanEnabled` is deliberately off to keep one span per message
on the high-frequency trade flow.
